# Pre-specified simulation study protocol

## 1. Objective

The simulation study evaluates the methodological properties of Outcome-Definition Sensitivity Analysis (ODSA) under controlled data-generating conditions. It is designed to answer four questions:

1. When does broadening a categorical outcome alter its level, association and group ranking?
2. How do state misclassification and group-size imbalance modify those changes?
3. Which definitions remain exactly recoverable after common forms of state coarsening?
4. Which diagnostics are required to prevent a broad outcome from supporting a claim that is semantically narrower than its positive class?

The simulation is not intended to reproduce the Romanian response set. It tests general properties of definition-sensitive categorical outcomes in an Information Systems setting.

## 2. Separation of simulation roles

Three principal profiles and one supplementary profile are maintained.

### 2.1 Smoke profile

The smoke profile contains three deliberately contrasting scenarios. Its only purpose is to detect software or configuration failures quickly.

### 2.2 Continuous-integration profile

The CI profile contains 96 scenarios and is executed with a small number of replications on every relevant branch update. It checks deterministic scenario construction, output schemas, recoverability boundaries and the complete analysis path. CI results are not journal evidence.

### 2.3 Article profile

The article profile contains 972 scenarios. It is the primary simulation design for the manuscript. The final frozen run will use 1,000 replications per scenario, producing 972,000 independent replications before the separate group-count robustness analysis.

### 2.4 Group-count robustness profile

The robustness profile contains 144 scenarios with two or five groups. Its final frozen run will use 1,000 replications per scenario, producing 144,000 additional replications.

The article and robustness profiles will be executed only after the code, scenario registry, seed policy and output schema are frozen. Any subsequent change requires a new versioned simulation run and a documented reason.

## 3. Fine-grained state space

The simulation uses five mutually exclusive fine states:

\[
S=
\{\text{active use},
\text{deployment},
\text{testing},
\text{planning},
\text{no engagement}\}.
\]

These states are ordered conceptually but ODSA does not require a scalar maturity score.

Four outcome definitions are registered:

\[
d_A=\{\text{active use}\},
\]

\[
d_I=\{\text{active use},\text{deployment},\text{testing}\},
\]

\[
d_B=\{\text{active use},\text{deployment},\text{testing},\text{planning}\},
\]

and the deliberately overlapping definition

\[
d_S=\{\text{active use},\text{planning}\}.
\]

The first three are nested:

\[
d_A\subset d_I\subset d_B.
\]

The fourth overlaps \(d_I\) but is not nested within it. This provides a controlled test of the requirement to distinguish nested broadening from overlapping operationalisations.

## 4. Base state distributions

Three base profiles are used:

| Profile | Active use | Deployment | Testing | Planning | No engagement |
|---|---:|---:|---:|---:|---:|
| Balanced | 0.20 | 0.15 | 0.15 | 0.20 | 0.30 |
| Active sparse | 0.08 | 0.12 | 0.18 | 0.27 | 0.35 |
| Project heavy | 0.10 | 0.22 | 0.24 | 0.29 | 0.15 |

The profiles represent substantively different points in an organisational technology-engagement process. None is presented as a population estimate.

## 5. Group-specific signal patterns

Groups are located at evenly spaced positions on \([-1,1]\). State probabilities are generated by adding pattern-specific shifts to the log probabilities of the base profile and applying a softmax transformation.

Six patterns are pre-specified:

1. **None** — no systematic group gradient.
2. **Active gradient** — active use increases across groups while project states change little.
3. **Project gradient** — deployment, testing and planning increase while active use remains comparatively stable.
4. **Reinforcing** — active use and project states increase in the same direction.
5. **Opposing** — active use increases while project states decrease.
6. **Pipeline substitution** — active use decreases while project-stage engagement increases.

The opposing and substitution patterns are especially important because they can produce attenuation, cancellation, direction reversal or rank reversal when project-stage cases are added to active use.

## 6. Sample size and imbalance

The core article profile uses three groups, matching the most important organisational-descriptor application in Study 1.

Nominal sample size per group takes the values:

\[
n_g\in\{50,150,500\}.
\]

Two group-size structures are used:

- balanced, with ratio 1:1;
- imbalanced, with a largest-to-smallest ratio of 4:1 and geometric spacing between groups.

The mean group size remains approximately equal to the nominal value. The analytical denominator is locked within each replication and retained after misclassification and coarsening.

## 7. Misclassification conditions

Three primary measurement conditions are included:

1. **None** — the recorded fine state equals the generated state.
2. **Adjacent symmetric, 10%** — each state has a 0.10 probability of being recorded as an adjacent state on the engagement continuum.
3. **Optimistic project-to-active, 10%** — deployment, testing and planning each have a 0.10 probability of being recorded as active use.

The first provides a clean baseline. The second represents non-directional classification noise. The third represents a substantively plausible optimistic coding mechanism in which project activity is reported as realised use.

A pessimistic active-to-deployment mechanism is implemented and tested but is reserved for supplementary sensitivity analysis rather than the core factorial design.

The misclassification matrix is row-stochastic and applied independently to the generated count in each true state.

## 8. Coarsening conditions

Three reporting structures are evaluated.

### 8.1 Fine

Every generated state remains separately observed.

### 8.2 Project collapsed

Deployment, testing and planning are merged into one `project_stage` state. Active use and no engagement remain separate.

Under this structure:

- \(d_A\) is recoverable;
- \(d_B\) is recoverable;
- \(d_I\) is not recoverable because the project-stage fibre contains planning, which is excluded from \(d_I\);
- \(d_S\) is not recoverable.

### 8.3 Binary engaged

Active use, deployment, testing and planning are merged into `engaged`.

Under this structure:

- \(d_B\) is recoverable;
- \(d_A\), \(d_I\) and \(d_S\) are not recoverable.

Non-recoverable definitions are reported as such. They are not reconstructed through proportional allocation, imputation or an unreported assumption.

## 9. Core factorial design

The article profile crosses:

- 3 base profiles;
- 6 group-signal patterns;
- 3 nominal sample sizes;
- 2 imbalance conditions;
- 3 misclassification conditions;
- 3 coarsening conditions.

This yields

\[
3\times6\times3\times2\times3\times3=972
\]

pre-specified scenarios.

With 1,000 replications per scenario, the core analysis contains 972,000 replications.

The group-count robustness profile crosses:

- 3 base profiles;
- 6 signal patterns;
- group counts of 2 and 5;
- nominal sample sizes of 100 and 500;
- balanced group sizes;
- no misclassification and adjacent symmetric misclassification;
- fine-state observation.

This yields 144 scenarios and 144,000 replications.

## 10. Random-number policy

The master seed is:

```text
20260814
```

Each replication receives a deterministic child seed derived from:

- the master seed;
- the numeric scenario identifier;
- the replication number.

Consequently:

- scenario ordering does not alter the random stream of another scenario;
- sharding does not alter results;
- re-running one scenario reproduces the same observations;
- adding a later scenario does not silently change earlier results.

The scenario registry is written before simulation and included in the archival release.

## 11. Primary estimands

### 11.1 Level sensitivity

\[
\Delta_L=L(d_B)-L(d_A).
\]

For nested definitions this quantity is non-negative by Proposition 1.

### 11.2 Semantic contamination of an active-use claim

\[
K_A(d_B)=1-\frac{L(d_A)}{L(d_B)}
\]

when \(L(d_B)>0\). This is the share of broad positives that do not satisfy the active-use definition. The term *contamination* is claim-relative: it does not imply that project states are erroneous or unimportant.

### 11.3 Association sensitivity

\[
\Delta_V=V\{d_B;X\}-V\{d_A;X\},
\]

where \(V\) is bias-unadjusted Cramér's \(V\). The following are reported:

- the mean and quantiles of \(\Delta_V\);
- the proportion of replications with \(\Delta_V>0\);
- the proportion with \(\Delta_V<0\);
- the proportion with equality to numerical precision.

No monotone direction is expected.

### 11.4 Group-ranking sensitivity

For each definition, groups are ordered by their positive rate. ODSA reports:

- whether the order differs;
- the normalised Kendall inversion distance between the two orders.

### 11.5 Direction sensitivity

The signed contrast between the last and first group is computed under each definition. A direction reversal occurs when the contrasts have opposite signs.

### 11.6 Misclassification bias

For \(d_A\) and \(d_B\), the recorded fine-state level and Cramér's \(V\) are compared with their true-state counterparts.

### 11.7 Recoverability

For every definition, ODSA reports whether membership is constant within every coarsening fibre. Non-recoverability is a structural result rather than a sampling error.

## 12. Secondary estimands

Secondary analyses will include:

- comparison of \(d_I\) with \(d_A\) and \(d_B\);
- overlapping-definition diagnostics involving \(d_S\);
- pessimistic active-to-deployment misclassification;
- sensitivity of ranking results to group count;
- Wilson interval coverage for definition-specific levels;
- numerical stability under small or sparse margins.

These analyses are labelled supplementary and cannot replace the primary estimands after results are known.

## 13. Monte Carlo precision

For a simulated proportion \(\hat{\pi}\) based on \(R=1{,}000\) independent replications, the Monte Carlo standard error is

\[
\operatorname{MCSE}(\hat{\pi})
=
\sqrt{\frac{\hat{\pi}(1-\hat{\pi})}{R}}.
\]

The worst-case MCSE occurs at \(\hat{\pi}=0.5\) and is approximately 0.0158. Scenario summaries report this MCSE for Boolean outcomes. The manuscript will not report trivial additional decimal places.

If an estimand central to the article has an MCSE that is too large for its interpretation, replications will be increased for all scenarios in the affected pre-specified profile rather than selectively for favourable conditions.

## 14. Analysis policy

The simulation is descriptive and diagnostic. Its purpose is to establish when definition-sensitive behaviour occurs, not to test a null hypothesis that ODSA has no effect.

The primary article will report:

- scenario-factor plots;
- distributions and quantiles;
- reversal frequencies;
- recoverability matrices;
- representative counterexamples selected by pre-specified criteria.

It will not treat simulation replications as empirical organisations or use their very large number to generate substantively meaningless p-values.

## 15. Representative counterexample selection

Counterexamples displayed in the manuscript will be selected by deterministic rules, such as:

- the smallest absolute \(\Delta_L\) among replications with a ranking reversal;
- the largest negative \(\Delta_V\) within a pre-specified signal pattern;
- the smallest sample scenario with a contrast-direction reversal;
- a coarsening condition that makes \(d_I\) non-recoverable while preserving \(d_A\) and \(d_B\).

No example will be selected solely because it produces the most visually dramatic support for the method.

## 16. Sharding and aggregation

The article profile may be divided across GitHub Actions jobs. Scenario assignment follows:

\[
\text{scenario index}\bmod \text{shard count}.
\]

Each shard writes:

- its scenario registry;
- replication-level output;
- scenario summaries;
- a design manifest.

Aggregation verifies:

- that every scenario identifier appears once;
- that every scenario contains the planned number of replications;
- that master seed, profile and software version agree;
- that output schemas are identical;
- that no respondent-level empirical data are present.

## 17. Failure handling

A simulation run fails if:

- a scenario identifier is duplicated;
- a scenario is omitted;
- row-stochasticity is violated;
- the denominator changes after misclassification or coarsening;
- a non-recoverable definition is silently estimated;
- the software version differs from the frozen release;
- a shard produces fewer replications than specified;
- generated outputs contain non-finite values outside explicitly nullable diagnostics;
- the release-boundary scan fails.

Failed runs are not partially pooled with successful runs.

## 18. Reporting boundary

The final manuscript will distinguish:

- properties proved mathematically;
- behaviour demonstrated by counterexample;
- frequencies estimated by simulation;
- patterns observed in Study 1;
- patterns replicated in Study 2.

This separation is essential. A simulation frequency is not a theorem and a single empirical application is not evidence that a behaviour is universal.

## 19. Current implementation status

The RC branch currently supports:

- all execution profiles;
- deterministic scenario registries;
- deterministic sharding;
- misclassification;
- coarsening and exact recoverability;
- level, association, contrast and ranking diagnostics;
- scenario-level summaries;
- Monte Carlo standard errors for Boolean estimands.

The smoke and CI profiles are software verification. The final 972,000-replication article run remains blocked until this protocol, the code and the output schema have passed the hostile internal audit.
